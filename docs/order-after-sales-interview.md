# 订单与售后案例：演示与面试材料

这份材料讲述本仓库的独立学习重构。它不代表 vivo 私有源码、实习期间生产上线或本人已验证的个人贡献。事实与归属按上层的《BlueCode 事实与贡献台账》A–D 分级：本仓库源码和离线记录属于可直接复核的 A 级项目证据；模拟模型行为不能推导真实模型表现；历史个人归属仍需本人用 PR、需求单或职责记录确认。

## 90 秒介绍

> 电商开发任务常见的错误不是代码无法运行，而是订单重试重复扣库存、取消订单重复释放库存，或部分退款只检查单次金额却越过累计上限。我在 BlueCode 的公开学习重构中，把这些规则拆成三份固定任务：T1 创建订单、T2 取消订单、T3 部分退款，并用独立 HTTP 验收检查正常流、异常状态、重试和边界。Agent 在独立容器里开发，验收器和参考答案不进入容器。评测设计固定免费模型、请求预算与安全策略，比较关闭压缩和 RTK＋Headroom 的组合。每次运行保留补丁、业务验收、provider usage 与压缩轨迹。现在离线参考实现和错误实现检查已通过，离线压力试跑证明两种压缩机制确实参与；16 次免费模型正式运行因缺少 Zen 凭据仍待执行，所以目前不报告任务正确率或 token 改善。

## 常见追问

**为什么答案里出现业务关键词不能算完成？** 订单可能仍被重复创建、库存仍可能为负；只有独立 HTTP 验收观察最终状态与响应，才算任务通过。公开 `bun test` 用于开发反馈，不是最终判定。

**如何证明压缩参与了？** 检查 `compressed: true` 对应的 RTK 前后长度，以及 Headroom 的生成、应用和下一次模型请求消费标记。若 Combo 未触发，结果标记 `compression_not_exercised`，仍留在分母中。

**为什么 Baseline 仍开启安全？** 这样两组只改变压缩能力。关闭整个插件会一并改变安全策略，使正确率与耗时无法归因。

**如何避免重复退款或释放库存？** T2 限定可取消状态、重复取消返回原结果且不再增库存；T3 对同订单的幂等键及请求体做一致性判断，同时校验累计数量和金额。失败时不提交任何状态变化。

**失败如何归因？** 分开记录业务验收失败、超时、预算耗尽、模型／代理错误、环境错误，以及压缩未触发。单靠轨迹仍不能把模型推理错误精确归因于某个历史约束；需要对比代码补丁、请求和外部验收。

**为什么不报成本或显著优势？** 免费模型零账单不等于成本下降；当前无在线 provider usage。即使完成两次重复，小样本也只能说明这三类任务的观察结果。

## 案例与简历候选文案

- **成功侧证据：**参考修复分别通过 T1/T2/T3 外部验收；验收器还拒绝十四份错误实现。这证明评测题和判定器的基本有效性，不是 Agent 成功案例。
- **失败复盘：**离线假模型运行 T3 压力任务，真实宿主工具与压缩链路完成，但未改动业务代码，四项退款验收均失败；失败类型为 `business_error`，实际 provider usage 缺失。这是 Harness 演示，不用于推断免费模型能力。
- **待补案例：**正式 16 次运行后，从完整账本选择一条真实通过和一条真实失败的 run，按“业务约束 → Agent 行为 → 压缩轨迹 → 外部验收 → 解释”展示，不挑样本替换失败。
